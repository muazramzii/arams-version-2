Scope, sources, and one missing input

Three sources of truth were specified for this audit: the ARAMS final report, the existing application, and the existing SQL data. Two of the three are present.

Blocking gap — the final report was not provided

The working directory contains the application source and arams_uthm.sql. It contains no report — no PDF, DOCX, or written specification of any kind. The complete file inventory is 104 application files plus the SQL dump.

What this changes. Everything in Part 1 below is derived from code and data, which is solid ground. But statements of intent — what ARAMS was specified to do, as opposed to what it does — rest only on the repository README.md and on your brief. Where the report would have settled a question, I have raised it under Decisions needed rather than guessing.

Ask. Please provide the report before Phase 2 sign-off. Several open questions — especially the intended validator role and the KPI measurement period — are exactly the kind of thing the report should answer.

What was actually examined

  • Source: every PHP, JS, and CSS file except the vendored PHPMailer library — 12,166 lines of PHP across two distinct application generations.
  • Schema: all 20 tables, 4 views, every index and foreign-key constraint in the dump.
  • Data: the dump was parsed into a scratch SQLite database and queried for integrity, orphans, duplicates, vocabulary drift, and workflow consistency. Roughly 1,130 rows of real UTHM lecturer and research data. Nothing was written back; the dump is untouched.

The system works for a demo and falls apart under institutional scrutiny. Three themes run through everything below:

  1. The authorization story is inverted. The AJAX endpoints are mostly well-scoped — the faculty checks in api/assign_kpi.php and api/analytics_detail.php are genuinely careful. The pages they support have almost no guards at all. Any lecturer who is logged in can read the whole institution's data by typing a URL.
  2. Validation is recorded, but not attributable. The schema can only name an admin as reviewer. TDPP is the only role the code lets validate. Every TDPP approval therefore writes NULL into the approver column, and the decision history is gone the moment it is made.
  3. KPI is not measuring anything. Progress is computed by counting a lecturer's entire lifetime of approved output, with no period window. One live task has a target of 1 and a progress of 19.
Part 1 — Audit
A

Existing system understanding

ARAMS is a working final-year project: a PHP/MySQL web application running on XAMPP that tracks UTHM lecturers' research output, routes it through a faculty-level approval step, and reports on it. It is real software with real data in it — 98 lecturer profiles, 278 research submissions, 107 publications, 71 grants — not a prototype with seed rows.

Name discrepancy

Your brief calls it the Academic Research Analytics and Monitoring System. README.md calls it the Academic Research Activity Monitoring System. The login page in index.php uses a third form, Academic Research Analytics & Monitoring System. Minor, but it needs one canonical answer before anything is branded.

What the system genuinely does today

  • Lecturers log in and submit five kinds of research record: publications, grants, H-Index snapshots, IP records, and research income.
  • Each submission enters a queue. A TDPP approves or rejects it with optional remarks.
  • Approved records feed dashboards, drill-down analytics, and exports. Pending and rejected records are excluded — this filter is applied consistently and correctly across every aggregate query I checked.
  • TDPP assigns KPI tasks to lecturers in their own faculty; approval of a matching record auto-completes them.
  • Admin manages users, edits selected fields, generates reports, and reads an audit log.
PreserveThings the existing system gets right

These are not accidents and should carry into 2.0 rather than being redesigned away:

  • The approved-only rule is honoured everywhere. Every dashboard, analytics query, and report joins rd.status = 'Approved' AND rd.is_deleted = 0. The core business principle of the system is intact.
  • Analytics drill-down scoping is correct. In api/analytics_detail.php, a lecturer's own ID and a TDPP's faculty ID take precedence over any client-supplied faculty_id. URL tampering on that endpoint does not work.
  • The grant level → category cascade encodes real UTHM/FRT vocabulary (Tier 1, RE-GG, GPPS, FRGS, PRGS, TRGS, LRGS, KKP, PPRN, Sepadan MTUN). That taxonomy is domain knowledge worth migrating verbatim.
  • The publication model already carries MyRA-relevant fields — quartile, indexing, impact factor, and the three collaboration flags. Someone thought about what the institution actually reports on.
  • Passwords are properly hashed (bcrypt, all 105 rows), login is rate-limited by IP, and the password-reset flow stores hashed OTPs with expiry and attempt counters.
B

Current architecture

There is no architecture in the formal sense. There is a directory of pages that each open their own database connection and write their own SQL inline. That is workable at this size; it is the reason the system cannot grow.

arams/ ├── index.php login page (live entry point) ├── pages/ ← generation 2, the live application │ ├── admin/ 10 pages │ ├── tdpp/ 6 pages │ └── lecturer/ 6 pages ├── api/ 21 AJAX endpoints (JSON + redirect responses) ├── includes/ header, sidebar, auth, csrf, mailer, │ research_insert, kpi_autocomplete ├── config/ database.php (PDO) · db.php (dead mysqli) ├── assets/ main.css (782) · main.js (425) · research_forms.js (197) │ ├── admin/ lecturer/ grant/ publication/ auth/ ← generation 1, dead └── dashboard.php login.php logout.php ← generation 1, dead
CriticalTwo application generations coexist, and the dead one is dangerous

The folders admin/, lecturer/, grant/, publication/, auth/ and the root dashboard.php / login.php are an abandoned first version. They connect through config/db.php to a database called arams_db (not arams_uthm) using tables — users, lecturers, projects, publications, students — that do not exist in the dump. They fail at connection time.

They still ship, they are still reachable over HTTP, and they contain textbook vulnerabilities:

login.php:10 $sql = "SELECT * FROM users WHERE email='$email'"; ← SQL injection login.php:16 if($user && $password==$user['password']) ← plaintext comparison

They also reference three modules that exist nowhere else in the system: Research Projects, Postgraduate Student Supervision, and pages for hindex/add.php, ip/add.php, income/add.php that were never built. Whether Projects and Students were dropped deliberately or simply never finished is one of the open questions in Part 3.

Structural characteristics of the live generation

  • No separation of layers. pages/admin/analytics.php is 1,072 lines of interleaved SQL, PHP, HTML, inline CSS, and JavaScript. lecturer_detail.php is 869. There is no model, service, or repository layer — SQL lives wherever it is consumed.
  • Two response conventions in one API folder. Some endpoints return JSON; login.php, update_profile.php, and generate_report.php issue HTTP redirects. Some read $_POST, others read a JSON body, and generate_report.php accepts either.
  • Deployment path is hardcoded. Every redirect and asset link is prefixed /arams/ literally, in dozens of files. The application cannot be mounted anywhere else without a find-and-replace.
  • Business rules live in the presentation layer. The "approved only" filter is retyped as a WHERE clause in roughly forty places. It is correct in all of them today, which is luck, not design.
  • Reference vocabularies live in JavaScript. Grant categories, publication types, author roles, indexing options, and a 190-entry country list are hardcoded in assets/js/research_forms.js and partially re-hardcoded in api/update_lecturer_admin.php. They are not in the database.

D

Current role and permission structure

Three roles, as specified: Lecturer, Admin, TDPP, stored as an ENUM on tbl_user. Each has a profile table — tbl_lecturer (98), tbl_admin (2), tbl_tdpp (5). The role model itself is sound. Its enforcement is not.

CriticalOnly one of 25 portal pages checks the user's role

I checked every page for a role guard. pages/admin/audit_log.php has one — it calls requireLogin() and then tests $_SESSION['role'] !== 'Admin' before emitting any HTML. It is the only page in the system that does.

Every other page simply includes includes/header.php, which calls requireLogin() and nothing more. requireLogin() checks that a session exists. It does not check who you are.

includes/header.php:7 requireLogin(); ← the only guard on 24 of 25 pages pages/admin/dashboard.php:7 require_once '../../includes/header.php'; ← no role test follows

Concretely: a logged-in lecturer who types /arams/pages/admin/dashboard.php gets the institution-wide dashboard. /arams/pages/admin/users.php gets the user directory. /arams/pages/admin/lecturer_detail.php?id=42 gets any colleague's full profile, email address, and complete research history — the page reads $_GET['id'] and looks it up with no ownership or role check whatsoever. /arams/pages/tdpp/validation.php gets another faculty's validation queue.

The README states that portals have "server-side guards" and that faculty scoping is "enforced server-side." For the AJAX endpoints that is largely true. For the pages, it is true exactly once.

StrengthThe endpoint layer is meaningfully better than the page layer

Worth stating plainly, because it should not be thrown away: 11 of 21 endpoints call requireRole(), and the KPI endpoints re-resolve the caller's TDPP identity from the session and verify both task ownership and the target lecturer's faculty before writing. api/delete_kpi.php refuses to delete another TDPP's task. pages/tdpp/lecturer_analytics.php — a page, unusually — checks that the requested lecturer is in the TDPP's own faculty and renders an Access Denied panel otherwise. Someone understood the requirement; it was applied unevenly.

Other authorization defects

  • No CSRF protection anywhere except the login form. includes/csrf.php is well written and is called by exactly one form. Every state-changing endpoint — approve, reject, assign KPI, delete KPI, edit records, change passwords — accepts a cross-origin POST.
  • Admin can reset any user's password via api/update_user.php with no audit entry, no notification to the account holder, and no old-password requirement.
  • A lecturer can change their own password without confirming the current one (api/update_profile.php), so a hijacked session becomes permanent account takeover.
  • Session fixation. No session_regenerate_id() on login.
  • Demo credentials are printed on the login page for all three roles (index.php, lines 118–122).
E

Current business workflow

The intended lifecycle is submit → validate → count. What is implemented is a two-state flag with no history, no return path, and a reviewer field that cannot hold the actual reviewer.

The submission lifecycle as built

StageImplemented?Evidence
DraftNoRecords are created directly as Pending
Submitted / PendingYesapi/submit_research.php:21
Under reviewNoNo claiming, no in-progress state
ApprovedYesapi/validate.php
RejectedYesRemarks stored in a single overwritable column
Revision requestedNoNot modelled
ResubmissionNoLecturer has no edit or resubmit control at all

pages/lecturer/research.php offers exactly one action: Add. There is no edit button, no delete, no resubmit. A rejected record displays its remarks and then sits there permanently. The lecturer's only recourse is to submit a brand-new record, which creates an unlinked duplicate and leaves the rejected original in the table forever. This is very likely a contributing cause of the 16 duplicate publication titles found in the data.

ContradictionAdmin cannot validate, despite the README, the comments, and 165 rows of history

Three sources disagree about who validates research.

api/validate.php:8 // Allow both Admin and TDPP to validate api/validate.php:9 if (($_SESSION['role'] ?? '') !== 'TDPP') { ... 'Unauthorized' ... }

The comment says both. The condition permits only TDPP. Meanwhile tbl_research_data contains 165 rows stamped admin_id = 1, and the README lists validation under Admin. So: the documentation and the historical data both say Admin validates; the running code says Admin is forbidden. Admin retains a side door — api/admin_add_record.php inserts records pre-stamped Approved, bypassing validation entirely.

This needs an explicit decision before the data model is fixed. See Decisions needed, D1.

CriticalEvery TDPP approval discards the identity of the approver

tbl_research_data has exactly one reviewer column, admin_id, with a foreign key to tbl_admin. A TDPP is not an admin and has no row there. So validate.php does this:

api/validate.php:33 $adminId = $isTDPP ? null : ($user['admin_id'] ?? null); api/validate.php:57 UPDATE tbl_research_data SET status=?, remarks=?, admin_id=?, validated_at=NOW()

Since only TDPP can reach this code, admin_id is written as NULL on every approval the system performs. The data confirms it: 108 of the 272 approved records have no approver recorded. The audit log partially compensates — it stores the acting user_id — but only 7 audit rows reference Research_Data against 272 approved records, so it is not a reliable substitute.

Institutionally this is the most serious data-model defect in the system. UTHM cannot answer "who approved this publication?" for most of its own validated research.

Workflow breakNew submissions notify Admin, who cannot act on them

api/submit_research.php:30 inserts a "pending validation" notification for every row in tbl_admin. It sends nothing to tbl_tdpp — the only role permitted to validate. The notification data shows this precisely: every "New … submission pending validation" row is addressed to user 1 or user 9, both admins.

KPI auto-completion

CriticalKPI progress counts a lecturer's entire career, not the target period

includes/kpi_autocomplete.php recomputes progress by counting all approved records of the matching type for that lecturer, ever. There is no period, no year, no "since assigned_date" filter — and tbl_kpi_task has no period column to filter on even if the code wanted to.

kpi_autocomplete.php:57 SELECT COUNT(*) FROM tbl_publication p JOIN tbl_research_data rd ON p.data_id=rd.data_id WHERE rd.lecturer_id=? AND rd.status='Approved' AND rd.is_deleted=0 -- no date bound of any kind live data: task_id 1 → target_count 1, progress_count 19, status 'Completed'

A task assigned today is marked Completed the instant any record is approved, credited against work published in 2016. The KPI module does not measure performance; it reports history.

CriticalTwo KPI criteria can never match the data they are meant to filter

Indexing. tbl_publication.indexing_type is a MySQL SET — legitimate values include 'Scopus,WoS'. The matcher compares with =:

kpi_autocomplete.php:65 $sql .= " AND p.indexing_type=?"; $params[] = 'Scopus'; → misses all 4 publications indexed 'Scopus,WoS'

Grant level. The criteria ENUM offers 'Universiti'. The stored data holds 'University' in 32 rows and 'Universiti' in 4. A university-level grant KPI silently ignores 32 of the 36 university-level grants.

Both defects fail closed and silently — the count simply comes back lower. Neither would ever surface as an error.

Two further KPI issues: progress can never decrease, because completed tasks are excluded from re-evaluation, so a record that is later soft-deleted or re-rejected leaves the KPI permanently satisfied. And Award-type tasks count rows from tbl_award, which has no validation workflow at all — unvalidated data feeding an official performance measure.

F.2 · The generic parent entity

Your brief asks directly whether tbl_research_data is necessary. It is a parent row carrying status, remarks, validated_at, lecturer_id, faculty_id, admin_id, and soft-delete fields; each of the five domain tables holds a data_id FK back to it.

The intent is right — separating workflow state from domain data is exactly what your brief calls for in §6, and this schema was already reaching for it. The execution has three problems.

StructuralOne submission can hold several unrelated research records

Nothing constrains a data_id to a single child. In the real data, 67 of 278 submissions hold more than one:

pub/grant/hindex/ip/income per submission count 1 / 0 / 0 / 0 / 0 (publication only) 104 0 / 0 / 1 / 0 / 0 (H-Index only) 86 0 / 1 / 0 / 0 / 1 (grant + income together) 60 ← 0 / 0 / 0 / 1 / 0 (IP only) 18 1 / 1 / 0 / 0 / 1 (publication + grant + income) 3 ← 0 / 2 / 0 / 0 / 2 (two grants + two incomes) 3 ←

A single Approve therefore validates a bundle. A reviewer who wants to accept the grant but query the income figure has no way to express that — the status column governs both. And because the type is inferred by checking which child table has a row (vw_pending_validation does exactly this with a CASE ladder), a mixed bundle reports as whichever type is checked first.

The second problem is the reviewer column, covered in section E. The third is that data_id is the only handle a child record has — the domain tables have no lecturer, no faculty, no owner of their own. Every query in the system must traverse the parent to answer "whose is this?"

Recommendation: keep the separation of workflow from data, discard this implementation. Give each domain entity its own owner and its own identity, and attach a proper submission record to it. Detail in sections K and L.

F.4 · Faculty and user relationship assessment

Faculty coverage is real but lopsided: FKAAS 77, FSKTM 8, FKMP 4, FKAAB 4, FPTV 3, FKEE 2. Six of the twelve faculties have no lecturers at all. TDPP coverage is 5 of 12 faculties. There is nothing wrong with the structure — tbl_lecturer.faculty_id and tbl_tdpp.faculty_id are both properly constrained — but the following is a genuine institutional-reporting defect.

CriticalA faculty transfer silently rewrites history — and it has already happened

tbl_research_data.faculty_id looks like a snapshot of the lecturer's faculty at submission time. It is populated in all 278 rows. It is never read and never written by any application code — the value exists only because the seed data set it. Both insert paths omit the column entirely, so any submission made through the running application today stores NULL.

Meanwhile every analytics, dashboard, and report query attributes research through tbl_lecturer.faculty_id — the lecturer's current faculty. The consequence is already visible in the data:

lecturer 1 Rozlini binti Mohamed current faculty: 6 (FKAAB) 37 submissions stamped faculty 1 (FSKTM) tbl_faculty_transfer #4: lecturer 1, FSKTM → FKAAB, 2026-06-19

When she transferred, 37 records of research output — publications from 2016 onward — moved with her. FSKTM's historical publication counts dropped; FKAAB's rose by work that was never done there. Neither faculty was told. Every year-on-year comparison in the system is now wrong for both.

The correct data is sitting in the column. Nothing reads it.

F.7 · Duplicates, orphans, and missing data

16 duplicate publication titles — every pair belongs to the same lecturer, so these are true duplicates rather than legitimate co-authorship. They are approximately 15% of the publication table and they are inflating that lecturer's counts, their faculty's counts, and the institution's totals.

11 duplicate grant codes (H937, Q940 three times, and nine others), again same lecturer and same role in every case. grant_code has no unique constraint.

One duplicate H-Index — lecturer 2 has two records for 2025. The unique key uq_hindex_year_lecturer(record_year, data_id) cannot prevent this: data_id is already distinct per submission, so the composite is unique by construction and constrains nothing. The constraint name states an intent the constraint does not implement.

No orphans in the referential sense — the foreign keys did their job. The orphans here are structural: 4 faculty-transfer rows and 12 KPI-target rows that no code will ever load.

F.8 · Legacy and dead fields

  • tbl_research_data.faculty_id — populated, never read, never written. Revive it properly or drop it.
  • tbl_research_data.admin_id — structurally incapable of holding the actual reviewer.
  • tbl_lecturer.research_group_category — duplicates information already implied by research_group_id, and disagrees with it.
  • tbl_lecturer.research_centre — free text overlapping tbl_research_group.
  • tbl_admin.name, tbl_tdpp.full_name, tbl_lecturer.full_name — the same attribute stored three times in three tables.
  • tbl_report.faculty_filter — a varchar holding what is really a faculty ID, with no FK.
  • tbl_grant.grant_category vs grant_level — overlapping taxonomies, both free text, both drifted.

F.9 · Constraint and vocabulary failures

CriticalThe database is silently rejecting values and storing empty strings instead

tbl_report.report_type is an ENUM of seven report names. api/generate_report.php writes 'publications', 'grants', 'comprehensive' — none of which are ENUM members. MariaDB in non-strict mode coerces an invalid ENUM to '' and continues. The result:

tbl_report.report_type distribution (57 rows) '' 52 ← invalid, silently coerced 'Faculty Performance Report' 3 'Individual Lecturer Report' 2

91% of the report log records nothing about what was reported. The same failure mode explains the empty strings in pub_type, author_role, grant_category, and research_group_category. The database is not running in strict mode, so type violations do not raise errors — they quietly become blanks. Any migration must enable strict mode, or ARAMS 2.0 will inherit the same silent corruption.

The root cause is that vocabularies live in JavaScript rather than in the database. assets/js/research_forms.js defines the grant level → category cascade, publication types, author roles, indexing options, and a 190-country list. api/update_lecturer_admin.php re-declares two of those lists inline as PHP arrays. The ENUMs in the schema are a third, divergent copy. Nothing keeps the three in sync, and the data shows all three drifting apart.

The authors field deserves specific comment. Given that every duplicate found belongs to a single lecturer, the current data does not yet distinguish these cases — but it will the moment a second faculty starts using the system.

F.11 · Indexing and performance

At current volume nothing is slow, so this is forward-looking. Existing indexes are reasonable — status, year, quartile, and faculty are all covered. Gaps and dead weight:

  • tbl_research_data.faculty_id — no index and no foreign key.
  • idx_grant_year on start_date — indexes a column that is 99% NULL.
  • uq_hindex_year_lecturer — unique on a pair that is already unique. Enforces nothing.
  • grant_code, publication.doi, ip_number — no unique constraints, which is why duplicates accumulated.
  • vw_lecturer_kpi left-joins five domain tables through one parent and aggregates in a single pass. Correct at 278 rows because each submission has at most one child of each type; it will produce inflated sums the moment that stops being true. It also computes "current H-Index" as MAX(hindex_value) across all years rather than the value from the latest year — a lecturer whose H-Index is recorded as 14 in 2024 and 12 in 2025 shows as 14.

F.12 · Migration posture

The data is small (~1,130 rows), referentially clean, and structurally comprehensible. Migration is entirely feasible and mostly mechanical. Full strategy in section U; the short version is that four things need human decisions rather than scripts: the 16 duplicate publications, the 11 duplicate grant codes, the 70 missing grant start dates, and the 77 shell accounts.

Four architectural commitments

  1. Authorization is a Policy, never a page. Every model gets a Policy. Faculty scoping is additionally enforced by an Eloquent global scope so that a forgotten where clause cannot leak data. The current system's failure was that scope was a habit applied per-query; in 2.0 it must be structural.
  2. Business rules live in Services. Submitting, transitioning, recomputing KPI, and generating a report are service methods with one implementation each. The "approved only" rule becomes a single query scope, not forty hand-typed WHERE clauses.
  3. Reference data lives in the database. Every vocabulary — publication types, author roles, grant categories and levels, income categories, IP types, departments, positions — moves into lookup tables with an is_active flag, served to the frontend by an API. One source, not three.
  4. State transitions are explicit and validated. A submission cannot move between statuses except through a declared transition, and every transition writes an immutable history row.

Deliberately not doing

No repository layer over Eloquent — it would add indirection without buying testability here. No CQRS, no event sourcing, no microservices. No polymorphic submittable relation unless D3 resolves in its favour; polymorphism costs referential integrity, which is precisely what this schema needs more of.

Unclear requirement — H-Index is not a submission

Found: H-Index is modelled identically to publications and grants — a lecturer submits it and a TDPP approves it. 87 rows exist, 77 inserted in a single automated batch.

Why ambiguous: H-Index is not an achievement a lecturer reports; it is a metric published by Scopus or Web of Science. Asking a TDPP to "approve" a number that Scopus computed is a review step with no real decision in it — the reviewer can only check that the lecturer copied it correctly.

Interpretations: (a) keep it in the workflow as today; (b) treat it as an institution-maintained metric snapshot, imported periodically by Admin, outside validation; (c) keep lecturer entry but auto-approve, with TDPP able to flag anomalies.

Recommended: (b), with (c) as a transitional step. It matches how the 77-row batch was actually created, and it removes 77 meaningless approvals from the validation queue.

Impact: changes whether hindex_snapshots carries a submission FK, and removes an H-Index KPI type. Needs your decision — see D2.

Three tables carry the entire workflow, replacing tbl_research_data.

State machine

stateDiagram-v2
  [*] --> DRAFT
  DRAFT --> SUBMITTED : lecturer submits
  DRAFT --> [*] : lecturer discards
  SUBMITTED --> WITHDRAWN : lecturer withdraws
  SUBMITTED --> UNDER_REVIEW : reviewer claims
  UNDER_REVIEW --> APPROVED : approve
  UNDER_REVIEW --> REJECTED : reject, remarks required
  UNDER_REVIEW --> REVISION_REQUESTED : request changes, remarks required
  REVISION_REQUESTED --> SUBMITTED : lecturer resubmits, revision + 1
  APPROVED --> SUPERSEDED : admin correction
  REJECTED --> [*]
  WITHDRAWN --> [*]
  SUPERSEDED --> [*]

REJECTED is terminal and REVISION_REQUESTED is not — that distinction is the point. Rejection means the record does not belong in the repository; revision means it does, once corrected. The current system collapses both into "Rejected" and then offers no way back, which is why lecturers resubmit as new records and duplicates accumulate.

Rules the state machine enforces

  • Only APPROVED submissions count toward analytics, KPI, and reports. One query scope, one definition.
  • A record can be edited by its owner only in DRAFT or REVISION_REQUESTED.
  • Rejecting or requesting revision requires non-empty remarks — enforced by a Form Request, not by convention.
  • A reviewer cannot decide on a submission they created.
  • UNDER_REVIEW records who claimed it, so two TDPPs in a large faculty do not duplicate work.
  • An Admin correction to an approved record creates a SUPERSEDED predecessor rather than an in-place edit — the current system's silent edits to approved data become traceable.

Unclear requirement — is a submission one record or a bundle?

Found: 67 submissions in the real data hold more than one research record, most commonly a grant plus its income (60 cases). The application only ever creates one child per submission, so these came from the bulk import — but the schema allows it and the reviewer UI cannot express a partial decision.

Interpretations: (a) one submission = exactly one record, and the grant/income pairs split into two submissions on migration; (b) submissions may bundle related records, with a decision per item.

Recommended: (a). It makes the state machine, the KPI matcher, and the reviewer UI dramatically simpler, and it matches what the application already does. The grant + income pairing is better expressed as the FK that already exists between them. Splitting the 60 pairs is a deterministic migration step.

Impact: determines whether submissions is one-to-one or one-to-many with research records. This is the single most structural open question. See D3.

M

Recommended KPI model

The current design has two disconnected halves: institutional targets nobody reads, and individual tasks that count the wrong thing. The rebuild unifies them under one concept — a measure evaluated over a period against a target.

TablePurpose
kpi_periodsNamed measurement windows — "2026", "2026 H1" — with explicit start and end dates and a lock flag. The missing concept in 1.0.
kpi_measuresWhat can be measured: entity type, aggregation (count or sum), the column summed, and the criteria schema. Replaces the ENUM in tbl_kpi_target and the criteria columns in tbl_kpi_task.
kpi_criteriaRows, not columns. measure_id, field, operator (=, in, >=, contains), value. Adding a criterion becomes data entry, not a migration.
kpi_targetsTarget value at a scope — institution, faculty, or individual — for a measure in a period. Unifies tbl_kpi_target and the target side of tbl_kpi_task.
kpi_assignmentsA target assigned to a named lecturer by a named TDPP, with a deadline and lifecycle. The task concept, cleaned up.
kpi_progressMaterialised progress per assignment: achieved_value, target_value, percentage, computed_at. Recomputed by a service, never hand-incremented.
kpi_contributionsWhich specific approved record credited which assignment. New and important — makes progress auditable and lets a lecturer see exactly what counted.

How progress is computed

  1. A submission reaches APPROVED. A domain event fires.
  2. The KPI service finds open assignments for that lecturer whose measure matches the record type and whose period contains the record's effective date — the publication year, grant start date, or income year, not the approval date.
  3. Criteria are evaluated from kpi_criteria rows. Set-valued fields like indexing_type use contains, not equality — fixing the Scopus/WoS defect structurally.
  4. A kpi_contributions row is written, progress is recomputed from contributions rather than incremented, and achievement is derived.
  5. If a record is later withdrawn, rejected, superseded, or soft-deleted, its contribution is removed and progress recomputes downward. Progress that can only rise is not progress.

Unclear requirement — what period does a KPI measure?

Found: tbl_kpi_task has a deadline but no period, and the matcher counts a lecturer's lifetime output. Task 1 shows target 1, progress 19.

Why ambiguous: "Publish 1 Q1 paper by 30 Sep 2026" could mean the paper must be published in 2026, approved in 2026, or simply exist by the deadline. Each gives a different number and a different meaning.

Recommended: credit by the record's own effective date — pub_year for publications, year_received for income, grant start for grants — because that is what MyRA and institutional reporting count. Approval date determines when it becomes visible, not which period it belongs to.

Impact: determines the entire progress calculation and whether the 9 existing tasks can be migrated with meaningful progress or must be reset. See D4.

  • All mutations are transactional; all writes are audited.

Recommended frontend architecture

src/ ├── app/ router, providers, layouts, error boundaries ├── features/ one folder per domain — the primary unit │ ├── auth/ components · hooks · api · schemas · types │ ├── research/ │ ├── submissions/ │ ├── kpi/ │ ├── analytics/ │ ├── reports/ │ └── admin/ ├── components/ ui/ (shadcn) · data-table · charts · states ├── hooks/ useAuth · usePermissions · useScope ├── lib/ api client · query client · formatters · rbac ├── types/ generated from API resources └── routes/ route tree with role-aware guards

Feature-first, not type-first. Grouping by components/, hooks/, services/ at the top level spreads one feature across five folders; grouping by feature keeps a change local. Shared primitives stay at the root.

Non-negotiables

  • Route guards are a convenience, not a control. The frontend hides what a role cannot use; the API refuses it. 1.0's central failure was treating navigation as authorization.
  • Four states for every async view — loading (skeleton, not spinner), empty (with the action that fills it), error (with retry), success. This is the largest single UX gap in 1.0.
  • Zod schemas are shared between form validation and API response parsing, and mirror the backend Form Requests. Server-side validation errors map back to fields.
  • One DataTable, one FilterBar, one ConfirmDialog, one StatusBadge. Every table in the system is pageable, sortable, and filterable because there is only one table.
  • Destructive and irreversible actions confirm, and name what will happen.
  • Accessibility is a build gate — keyboard reachability, visible focus, labelled inputs, AA contrast, live regions for async results.

Visual direction

Institutional, dense, quiet. A muted UTHM-derived palette with a single accent; colour reserved for status and semantics rather than decoration. Tabular numerals wherever figures align. Generous type hierarchy, restrained chrome, a persistent left navigation with clear role identity. Status must be legible without colour alone — shape and label as well as hue. No gradients, no glass, no animated counters.

Recommended backend architecture

app/ ├── Http/ │ ├── Controllers/Api/V1/ thin — authorize, delegate, respond │ ├── Requests/ validation + authorization per action │ ├── Resources/ serialization; never leak a raw model │ └── Middleware/ EnsureRole · ScopeToFaculty · AuditContext ├── Models/ Eloquent + global scopes + casts ├── Policies/ one per model, no exceptions ├── Services/ │ ├── Submission/ StateMachine · SubmissionService · ReviewService │ ├── Kpi/ ProgressCalculator · CriteriaEvaluator · Matcher │ ├── Analytics/ MetricRegistry · ScopeResolver · Aggregator │ └── Reporting/ ReportBuilder · Exporters ├── Events/ · Listeners/ SubmissionApproved → KPI, notify, audit ├── Enums/ SubmissionStatus · Decision · Role · AuditAction └── Support/ Affiliation resolver, period resolver

Three layers do the work: Form Requests own validation, Policies own authorization, Services own business rules. Controllers do none of the three. That is the whole discipline, and it is what the 1,072-line analytics page is the absence of.

Specific commitments

  • MySQL runs in strict mode. Non-negotiable — it is what let 52 invalid report types become empty strings.
  • PHP enums for every status and decision, so an invalid value is a type error rather than a silent blank.
  • Migrations are the only way the schema changes. No phpMyAdmin edits, ever.
  • Seeders provide reference data, ported from the JS constants that are currently the most complete source.
  • Uploads: whitelist extensions, verify content with finfo, re-encode images, store outside the web root, serve through a controller. Directly addressing the RCE in G.
  • Tests gate the roadmap. Feature tests per endpoint, policy tests per role boundary, unit tests for the state machine and KPI calculator. A role-boundary test suite asserting that each role is refused what it should be refused is the direct answer to 1.0's central defect.

Decisions needed before Phase 2 sign-off

Six questions where the sources disagree or the requirement is genuinely ambiguous. Each changes the data model. None should be resolved by guessing.

D1Who validates research — TDPP only, or TDPP and Admin?

Contradiction. api/validate.php permits only TDPP. Its own comment says both. The README lists validation under Admin. 165 rows in the live data are stamped with an admin as approver, and Admin retains an auto-approve bypass through admin_add_record.php.

Recommended: TDPP is the primary validator for their faculty; Admin can validate as a fallback for faculties without a TDPP (7 of 12 have none) and for escalation, always recorded as such. Remove the silent auto-approve path in favour of an explicit, audited "Admin approval" decision.

Impact: determines whether decided_by needs a role qualifier and whether the reviewer Policy admits Admin.

D2Is H-Index submitted research or an institutional metric?

Detail in section K. Recommended: an institution-maintained metric snapshot outside the validation workflow.

Impact: whether hindex_snapshots carries a submission FK; whether an H-Index KPI type exists; removes 77 no-op approvals.

D3Is a submission one record or a bundle?

Detail in section L. Recommended: exactly one record per submission; split the 67 existing bundles on migration.

Impact: the most structural of the six. Determines the submission cardinality, the reviewer UI, the KPI matcher, and migration step 7.

D4What period does a KPI target measure?

Detail in section M. Recommended: credit by the record's own effective date, not its approval date.

Impact: the entire progress calculation, and whether the 9 existing tasks migrate with meaningful progress or are reset.

D5May a TDPP see other faculties' aggregate performance?

Ambiguous. Your brief requires faculty-level boundaries and also asks for faculty comparison. Those pull in opposite directions for TDPP. Today the question does not arise because TDPP has no cross-faculty view.

Options: (a) own faculty only; (b) aggregate figures for all faculties, no lecturer detail outside their own; (c) anonymised benchmarking — "your faculty vs. institution median".

Recommended: (c). It preserves the boundary while making comparison useful, which is the point of a comparison.

D6Do Research Projects and Postgraduate Supervision return?

Found. The generation-1 tree contains lecturer/my_projects.php, lecturer/my_students.php, admin/projects.php, and admin/student.php. They query tables (projects, students) that exist in neither database. No trace of either concept survives in generation 2 or in the schema.

Why it matters: per your instruction not to drop features for convenience, I am flagging rather than deciding. Postgraduate supervision in particular is a standard MyRA research-performance dimension, so its absence may be an omission rather than a decision.

Recommended: treat both as out of scope for 2.0 unless the report specifies them, but design the research domain so a sixth entity type can be added without structural change. The report would settle this — another reason to provide it.

Smaller items I have assumed rather than asked

  • The system is named Academic Research Analytics and Monitoring System, per your brief, over the README's Activity Monitoring.
  • The institution-level role is called Admin in the application. TNCPI does not appear as a role. The tbl_admin comment "TNCPI administrator profiles" is legacy wording and will be dropped.
  • Awards are retained as a research entity, because KPI already scores against them.
  • Faculty transfer is restored as an Admin feature, since removing it is what caused the historical-attribution defect.
  • Soft delete stays, but as a separate concern from workflow status — the current schema lets a record be simultaneously Approved and deleted, and two rows already are.
